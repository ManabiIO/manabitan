## Mechanism and assembly assessment

The 21-line source addition scans 16 bytes when at least 16 logical input bytes remain. Three vector comparisons identify a quote, a backslash, or an unsigned byte below 0x20. Their combined bitmask identifies the first special byte. Control then enters the unchanged scalar quote/escape/control handling directly, without scanning that block again through the eight-byte loop. The existing eight-byte and scalar tails remain. Both the new loop and shared label are guarded by `__wasm_simd128__`.

Clang's emitted WebAssembly assembly, generated from the frozen sources with the manifest's compilation flags, confirms four inlined copies of this loop: `encode_term_content_token_binary_row`, `write_normalized_glossary_value`, `parse_value_span`, and `parse_composite_span_impl`. Each uses an unaligned `v128.load`, `i8x16.lt_u`, two `i8x16.eq` operations, two ORs, `i8x16.bitmask`, and `i32.ctz`. The compiler selects a 16-byte advance when the mask is zero; WebAssembly's zero-input ctz is defined. The special-byte branch bypasses the old `i64.load` loop. This is compiler-level assembly evidence, not browser JIT machine-code or speed evidence. The added branch and mask construction can still cost more for short strings.

The candidate module grows by 616 bytes (1.16%). Separate pinned builds with `-msimd128` removed produce exactly identical whole modules: 52,347 bytes, SHA-256 `529d64b94c85a64b4673b92016cd796278b813220eea25850a48ce85916ab8e2`. This establishes that the guarded fallback compiles to the unchanged scalar implementation.

Assembly evidence is retained in `parser-baseline.s` (SHA-256 `3ecf3168476032bf34a3ee3b5a0080b5b70c5feb4db98e2e6656ee107bca6d60`) and `parser-simd.s` (`b69511d5afcb1976bb28bcca42ead30337f396f15737eb2ea3077be88b771925`). These were generated by Clang `-S`, not disassembled from the linked module.

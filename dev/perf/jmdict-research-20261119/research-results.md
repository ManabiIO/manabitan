# JMdict import qualification — 19 November 2026

## Decision

No completed screen yet establishes a production browser win. The aligned recent-content cache copy has favorable cache-phase direction in 16 of 18 pairs across two independent cohorts, with noisy effect magnitude and no established whole-import gain. [Draft PR #758](https://github.com/ManabiIO/manabitan/pull/758) presents this narrower claim for review and has not been merged. SIMD string scanning reduces aggregate parser work and part of the critical path in its first screen, but total browser time worsens; its independent twelve-pair replication is neutral and does not reproduce the target effect, so no SIMD product PR is proposed. Reject canonical counter caching for production: it slows its targeted phase in five of six browser pairs. Parser escape specialization, worker prewarming and the close-comma shortcut do not establish browser gains. Contiguous metadata publication has favorable exclusive-phase direction in 16 of 18 pairs, but both cohorts fail to improve integrated browser time; it remains unqualified with no product PR. Compression dispatch coalescing reduces measured post counts and native sample counts, but its small favorable browser direction remains inside noise in both cohorts and compression timing is inconsistent. It remains unqualified with no product PR. All thirteen planned browser cohorts are complete. Direct record-field access and manual Uint32 copying are rejected after local component screens. Both baseline traces attribute the approximately 112 ms finalization tail to a blocking native durability flush; changing cooperative yields does not address that measured cause.

## Fixed measurement and correctness protocol

Research branch `perf/jmdict-qualification-20261119` uses the unchanged release build and import harness, fixed baseline `d829f5b6e6a75ee8859d38d537d224ec33c4930e`, and pinned JMdict archive. Each initial Ubuntu screen builds both arms before measurements and executes the predetermined order: one excluded AB warmup, one AA control pair, six adjacent AB/BA alternating pairs, one BB control pair, then separate A/B CPU traces. The independent cache, SIMD, metadata and dispatch replications freeze twelve alternating pairs beginning BA, with their warmups also beginning BA. Only the research wrapper's validated pair-count/order options change; the product, import measurement harness, flags and baseline remain unchanged. No observation, tail, or control is discarded. Traces are diagnostic and excluded from speed estimates.

All completed initial screens passed 18 ordinary observations plus both diagnostic runs; each cache, SIMD, metadata and dispatch replication passed 30 ordinary observations plus both diagnostics. Across nine initial/calibration cohorts and four independent replications, all 308 reports validate: 282 ordinary observations and 26 separate traces. Traces, warmups and same-code controls remain excluded from paired speed estimates. Validation checks title/revision, 526,942 term rows, 12 content probes, their output digest, and the same receipt after a browser restart. Every ordinary observation has effective worker flags and package/source identity receipts. Corpus/output digest equality is necessary correctness evidence, not exhaustive browser-output equivalence; the component correctness suite complements these probes.

The remote environment is Ubuntu x64 with 4 available CPUs, Node 22.22.0, and the locked Playwright Chromium 153.0.8010.12. The control, parser-escape, initial SIMD and cache-replication cohorts used AMD EPYC 9V74 hosts; prewarming, initial cache-copy, canonical-counter, close-comma and both metadata-publication cohorts used AMD EPYC 7763 hosts. The independent SIMD replication used an Intel Xeon Platinum 8573C host; both dispatch cohorts used AMD EPYC 9V45 hosts. Production defaults select three parser workers, twelve groups and four groups per worker. Compare arms within a job, not absolute times across hosts. This does not establish Safari, Firefox, low-memory-device, or whole-browser memory performance.

## Critical path and trace evidence

Across the identical-product cohort's twelve measured observations, median browser import time is 940.25 ms and worker RPC time 914.75 ms. The principal sequential importer phases are archive/index 8.5 ms, import-data-banks 752 ms and bulk-finalization 139 ms. The nested term fast path is 722 ms. Worker totals, sink time and detailed subphases overlap and must not be summed as independent wall-time contributions.

### Recent-content cache copy

In the two baseline traces, `_cacheRecentPublishedTermContentSources` contributes 537/553 self samples. Its `spans.buffer.slice(minimumOffset, maximumEnd)` line accounts for 434/439 of these samples and 100.95/130.86 ms of sampled intervals. Other loop lines each account for approximately 1–5 ms. Ordinary reports record 100,724,405 cache-copy bytes in every run and approximately 117.5 ms median cache time. A private owned copy must remain because parser shared-memory storage can subsequently be reused.

Official V8 sources corroborate the alignment hypothesis: both same-type typed-array `slice` and `set` take a relaxed shared-memory move path. For nonoverlapping copies, the implementation aligns the destination and uses machine-word operations only when source and destination are both aligned; otherwise it falls back to byte operations. Plain `set` is therefore not automatically a solution for misaligned sources. These source references explain the mechanism but are not an exact revision match to the Chromium binary:

- <https://chromium.googlesource.com/v8/v8.git/+/refs/heads/main/src/base/atomicops.h>
- <https://chromium.googlesource.com/v8/v8/+/dc5908fd731c73e02c329b9336af6940ca70ae3d/src/builtins/typed-array-slice.tq>
- <https://chromium.googlesource.com/v8/v8/+/dc5908fd731c73e02c329b9336af6940ca70ae3d/src/builtins/typed-array-set.tq>

The cache candidate's diagnostic trace explains why the improvement is smaller than an all-misalignment component screen might suggest. Of its 130.93 ms sampled in `copyRecentTermContentSource`, the already-aligned/plain-`set` branch accounts for 100.58 ms (319 samples), the adjusted-source bulk copy 25.83 ms (87 samples), and private `copyWithin` 0.87 ms (3 samples). This establishes where sampled copy time goes, not exact byte or group shares. The local screen's full native slabs contain 100,725,122 bytes, whereas actual cache admission selects 100,724,405; native base alignment alone does not establish each selected minimum offset. The change retains an exact-size private owned buffer and the same cache byte budget.

### Remaining CPU and ownership leads

After cache copying, importer-worker self samples concentrate in canonical deduplication scanning (64/75 ms), garbage collection (56/45 ms), compression-worker `postMessage` dispatch (27/28 ms), in-flight source validation (24/29 ms), metadata publication itself (20/33 ms), record-field encoding (23/30 ms), lookup chunk assembly (28/19 ms), and reference-slab construction (21/17 ms). These are sampled intervals, not benchmarked component costs.

The metadata candidate's trace confirms its new contiguous helper runs: 68 self samples in the helper and zero in the staged-index resolver, compared with eight resolver samples in the baseline. The wrapper's self interval falls from 31.59 to 12.32 ms, but the new helper contributes 36.95 ms; ignoring that transferred work would misattribute a gain. The diagnostic exclusive publication phase is 54.6/40.3 ms, with substantial trace overhead. Those two diagnostic runs remain excluded from qualification.

The in-flight source registration retains borrowed buffers and validates bounds/aliases; it does not copy their payload. Compression dispatch already snapshots offset/length columns once into shared storage and sends views, so there is no whole-metadata clone per dispatch. `contentMetadataIndexPublishMs` includes recent-source caching and must not be added to cache time. Possible later work is allocation reduction in record-field/lookup assembly or dispatch batching, subject to exact ownership and cancellation checks; neither is currently a proven win.

The parser's largest sampled native functions are composite-span scanning, the fused parser, libdeflate, CRC32 and row parsing. Function IDs 37/31/41/2/11 were mapped using same-recipe named WASM builds with byte-identical non-custom sections. IDs match in the baseline, escape, close-comma and SIMD candidates. The [SIMD function map and section-identity receipt](validation/simd-function-map.json) are retained. This mapping does not turn parallel sample totals into critical-path wall time. Explicit `copy_valid_utf8` samples (function 28) account for only about 4–10 ms per baseline parser worker. The fused production path calls that function directly, so this cost is not substantially hidden in function 31; it is a lower-priority target than the dominant scans and cache copy.

For the separate canonical-deduplication module, `scan_canonical` is native function 4. Its 260/252 importer-worker samples account for 63.964/74.612 ms directly in the export. The JavaScript `_scan` wrapper contributes only 23/20 self samples and 6.341/8.487 ms; setup closures contribute 1.907/3.813 ms. Pending-column adoption adds 6.266/5.285 ms and exact byte comparisons 3.436/6.784 ms. Thus the canonical native loop itself, rather than an arena allocation or JavaScript copy, is a defensible target for a separately qualified change preserving the mutation journal and rollback barriers.

### Compression dispatch attribution

Native `postMessage` frames must be attributed to their JavaScript parent call site. In the first dispatch screen, importer-worker samples with parent `zstd-term-content.js` total 140 samples with 42.419 ms of signed raw sample-delta weight for the baseline and 63 samples with 28.319 ms for the candidate. The baseline caller is the dispatch closure at line 335; the candidate caller is `_postQueuedCompressionJobs` at line 334. These are diagnostic sample weights, not message counts, CPU-time estimates, or a measured 14.1 ms synchronous saving. The original identical-product traces attributed 26.966/28.377 ms to that same baseline native call.

JavaScript self samples alone at those call sites total only 0.313/0.109 ms and omit the native frames. An initial self-only reading was corrected before the qualification decision; those figures do not establish near-zero dispatch cost or a hardware-specific mechanism. The durable analyzer and exports now include `nativePostMessageByCaller`, so the native work remains auditable. Independent `SchedulePostMessage` events confirm the intended 102-to-48 compression-post reduction. The native sample count also falls. Exact duration attribution is sensitive to negative source deltas and how gaps are assigned: positive-only raw weights are 45.077/28.729 ms, while a following-gap interpolation gives 39.411/39.102 ms. Every selected native sample and positive raw interval lies inside an importer task, but none of these interpolation alternatives is a full DevTools duration model. The [independent audit](validation/dispatch-trace-independent-audit.json) preserves all 203 selected native samples, 150 compression-post events, source/trace hashes and duration conventions. These conventions do not justify an exact CPU-saving claim. Compression-phase wall time in the first screen remains neutral and browser controls are noisy. The independent replication again has fewer native samples (118/67), while signed raw weights reverse direction to 21.296/37.804 ms. That further limits any exact time-saving interpretation of sampled weights.

## Rejected local components

### Direct record-field access

Candidate `1abf32cb49a8fdce289909c97737a91071457cc6` removes some field access overhead but increases the full validation/layout/encoding boundary. The fixed component design uses 32 isolated Node children: eight alternating A/B pairs plus four AA and four BB control pairs. Each child runs two excluded warmups and eight measured full-corpus passes over the production twelve groups. Every input and output digest matches for all 526,942 rows and 4,229,084 encoded field bytes.

The candidate is slower in six of eight A/B pairs. Median paired change is +25.42%, and equal-work change is +8.51%. Median validation time across child means rises from 7.915 to 13.397 ms; field encoding falls from 11.982 to 10.328 ms. Measuring encoding alone would therefore select the wrong result. Same-code labeled control medians are −3.37% (AA) and +12.73% (BB), so the precise regression magnitude is uncertain. The unfavorable complete boundary supports rejection. See [every child observation](components/record-fields-cohort.json), the [recomputed summary](components/summary.json), and the archived component runner/driver and [exact rejected patch](components/record-fields-candidate.patch) beside them. This component excludes persistence and UI work and uses synthetic content references; it is not a browser speed estimate.

### Manual Uint32 copies

Both four-word and eight-word unrolled copy prototypes are rejected. The fixed Node 24 screen covers all eight byte alignments, five arms, two excluded warmups and eight rotating-order measured passes, for 320 measured outputs. All output hashes match. Separate parity covers 42,592 cases and 85,184 method calls. Relative to the aligned typed-array helper, median paired regressions range from 38.0% to 93.0% for the four-word loop and 16.4% to 69.1% for the eight-word loop across alignments. Large outliers remain in the record; aggregate means do not establish a precise effect size.

The screen uses full 100,725,122-byte native canonical slabs, distinct from the browser's 100,724,405-byte admitted cache selections. No product source was changed for these prototypes. See the [copy-screen summary](components/uint32-copy-screen-summary.json), [all measurements](components/uint32-copy-screen.json), [identity manifest](components/uint32-copy-screen-manifest.json), and [parity receipt](components/uint32-copy-parity.json).

### Canonical native replay

The [canonical replay](components/canonical-scan-replay.json) restores twelve full 25 MiB pre-call arena snapshots and verifies complete post-call memory, header and output hashes across 48 observations. Both modules match in every observation. Its warm native-only A/B timing appears favorable, but same-code ranges and extreme outliers are large. That result cannot override the fresh-browser target regression documented above. The replay remains useful as a correctness fixture for future native changes.

## Next steps

Contiguous metadata publication completed both cohorts with favorable exclusive-phase direction but no whole-import gain. Further work would need to explain surrounding cache and pipeline costs before reconsidering this version. Its target is the exclusive publication loop: subtract `dedupRecentSourceCacheMs` from `contentMetadataIndexPublishMs` in each observation before pairing, because caching is nested inside publication. Existing baseline observations put the exclusive loop around 19–34 ms. Repeated staged-index witness checks contribute approximately 5–10 ms of direct self intervals in several traces, without native calls or table probes. Preserve witnesses, transaction boundaries and rollback behavior while checking any reduced per-row work.

Compression transport coalescing completed both cohorts without establishing an integrated performance gain. Exact untimed reconstruction of all twelve native snapshots finds 102 blocks/posts with group counts 9, 9, 9, 9, 9, 9, 7, 8, 8, 8, 8 and 9, using the database's 1 MiB target. Grouping requests per worker could reduce outgoing posts to 48 while preserving each block's compression, ordering, source-consumed receipt and error-drain behavior. The current thirteen-Boolean experiment object is only 516 JSON bytes; reducing flags alone would save approximately 48 KiB across the import, so batching calls is the more substantial hypothesis. These are workload-shape facts, not timing evidence. See [validated dispatch shape](components/compression-dispatch-shape.json).

Both metadata publication and dispatch remain unqualified for production changes. A future combined cache/publication experiment must measure their interaction rather than adding isolated phase point estimates: the unchanged cache phase became slower during the metadata cohorts, and the exclusive publication improvement did not translate into faster imports. Further allocation work in lookup assembly is possible, but the rejected record-fields boundary shows why an isolated subphase improvement must be checked against surrounding validation and fresh-browser behavior. Whole-browser memory remains unmeasured; use the separate diagnostic below before claiming a memory gain.

## Memory interpretation

Existing telemetry reports a maximum individual parser WASM heap of 38,928,384 bytes, 36,040,000 metadata allocation bytes and 29,885,576 reused lookup-scratch bytes. It does not report peak whole-process or whole-browser memory. Current normal observations disable process sampling; the harness's optional sampler covers one browser PID rather than the browser process tree. No total-memory improvement is claimed. The [cache/gather ownership assessment](validation/cache-gather-reuse-assessment.md) identifies no existing independently owned raw JavaScript slab to adopt on the measured route: Zstd gather storage belongs to reusable worker-local WASM memory, while parser content is borrowed shared storage. Removing the copy would require a new ownership/publication protocol and separate validation.

A separate timing-free diagnostic could sample `/proc` descendants, recording PID/start-time/role and process-tree proportional-set-size (PSS) where readable. Summing RSS overcounts shared pages, including shared WASM memory. Keep this diagnostic separate from the authoritative cohort and retain the production worker/group policy and source lifetimes.

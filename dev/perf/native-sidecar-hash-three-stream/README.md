# Three-stream checksum and first-pass follow-up

Research only. The original single-stream module and warmed study remain
unchanged on `perf/native-sidecar-hash-20261128-beb5`, commit
`36f9ae58cde3a302cb2129e2af6cc86512d14fa1`.

## Preserve the negative result

The first hosted warmed study found **JMdict 42–44% slower** with single-stream
SIMD on an Intel Xeon 6975P-C, with A/A ratios within 0.2% of parity. Three
independent processes measured approximately 4.04–4.07 ms for JavaScript and
5.76–5.79 ms for native over all 23,748,240 checksum bytes. Jitendex on an AMD
EPYC 9V74 was only 2–4% faster, about 0.07–0.11 ms over its entire checksum
corpus. Hardware differs, so these are not dictionary-specific conclusions.
The complete round totals are preserved in `prior-single-hosted.json`.

The separate first-pass study addresses a different, pre-identified risk:
the warmed screen repeats each group many times, while a fresh JMdict import
hashes 36 large sections once. An isolated first section showed substantial
JavaScript tiering cost, but that single sample cannot establish the complete
corpus or browser result. This follow-up does not replace or discard the
negative warmed result.

## Three independent native streams

The prototype interleaves the three existing XXH32 states for base, derived,
and record fields. It uses a single fixed 64 KiB module memory, split into
three 20 KiB scratch windows, and hashes each original span independently with
the existing seed. Three-, two-, and one-stream loops handle unequal lengths;
each stream retains its own carry, wrapped length, and stripe flag. No hash
is reused across calls or an await. All input copies and admission checks
remain inside the synchronous call.

Independent oracle checks passed 105,768 hash comparisons, 36 rejected calls
that preserve every state, and 13,092 zero-length updates. Cases include
heterogeneous lengths and partition schedules, all short first splits, resets,
finish continuation, fixed memory, and input immutability. The checked-in
4,374-byte module is generated by pinned Clang 21.1.8/LLD 21.1.8. The wrapper
uses the same ordinary-view admission restrictions as the single-stream
prototype. Unsupported inputs fall back before native state changes.

Local first-group screening found triple-stream/JavaScript medians of 0.625,
0.640, and 0.690 for JMdict, Jitendex, and VNDB, respectively. A/A controls were
0.913, 1.045, and 1.048 on this noisy host. These results authorize further
component study only; they do not establish a browser or whole-import gain.

## Registered hosted protocol

The dedicated workflow runs one locked dictionary per Ubuntu 26.04 matrix job,
Node 22.22.0, and pinned Clang/LLD 21.1.8. It byte-compares regenerated modules
and runs independent vector checks in separate processes. It then captures
all current-policy groups with the unchanged capture tool. Source lock hashes,
archive hashes, group scope, and complete row counts are mandatory gates.

The warmed three-algorithm comparison runs seven seeded balanced-order rounds
with four repetitions and A/A controls. Its outcome remains separate from the
first-pass result.

The first-pass campaign registers eight JavaScript/single-stream pairs, eight
JavaScript/three-stream pairs, and eight independent JavaScript/JavaScript
control pairs: 48 fresh Node processes per dictionary. Arm order alternates
AB/BA by pair, and scenario order rotates. No primitive warmup, comparator hash,
repetition, trimming, or selective retry occurs. Node's compile cache is
disabled. Each section is SHA-verified before measurement and checked against
its expected XXH32 afterward, without running a comparator checksum.

Each child reports helper-module load, WASM file read, compile/initialization,
checksum elapsed time, and their inclusive total separately. Fixture reads,
SHA verification, and result checks are outside the component total; complete
process wall time is also preserved. Every raw process observation and failure
is retained. Node and Chromium have different tiering/startup behavior, so a
positive first-pass result still requires a browser component and complete
import qualification before runtime integration or a PR.
